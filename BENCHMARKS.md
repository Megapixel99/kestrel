Generated by `bench/compare.py` from the data in `results/`. Every number below is
reproducible; nothing here is transcribed by hand.

The point of this file is the gap between the two halves. The simulation and the
real engine were given the same policy and the same workload shape, and disagree by
about 4x — for one identifiable reason, recorded in RESULTS-ENGINE.md.

### Reduction vs unmanaged, by distribution

| distribution | Kestrel | discard-LRU | Kestrel state lost | LRU state lost |
|---|---|---|---|---|
| Chrome, ps sample | **8.9x** | 5.5x | 0 | 2453 |
| Firefox, 16 tabs | **10.9x** | 5.4x | 0 | 2494 |
| Chrome, 11 tabs + Meet calls | **7.9x** | 6.2x | 0 | 2332 |
| Firefox, 11 matched tabs | **11.5x** | 6.5x | 0 | 2464 |
| Chrome, same 11 tabs | **5.4x** | 5.4x | 0 | 1525 |

Kestrel loses no state in any configuration; discard-LRU destroys tabs in all of
them. That difference, not the memory ratio, is what the non-destructive ladder buys.

Note the last row. On the lightest-tailed distribution the memory advantage
disappears entirely — both policies land at the same mean — and the only thing
separating them is that one destroyed 1,525 tabs to get there. The ladder's memory
benefit tracks the tail of the distribution; its state-preservation benefit does not.

## Real engine — the same policies on WebKit

Run by `kestrel bench`, one policy per process. These are measured, not modelled.

Two totals per row. **attributed** is the per-tab sum — one process id per tab —
and **measured** is every WebContent process the run started, summed. They differ
because a demoted tab releases its web view while WebKit keeps the process alive,
so that memory stops being attributed to anything. The gap grows with how much a
policy demotes, which is the axis this table exists to compare, so the attributed
column is the one to distrust.

At a budget that clears the engine's hibernation floor, Kestrel is **1.24x** below unmanaged (measured totals) and destroys **6** tabs, where discard-LRU destroys **8**.

## Why the two halves disagree

| | simulated | measured on WebKit |
|---|---|---|
| a hibernated (COLD) tab costs | 32 KB | **39 MB** |
| a frozen (WARM) tab retains | 2-50% of live | **83%** of live |
| restoring a hibernated tab | assumed | **82 ms** to didFinish |
| reduction vs unmanaged | 7.9-11.5x | 1.4-2.6x |

The COLD row explains nearly all of it. WebKit will not terminate a renderer on
request — verified three ways — so a hibernated tab keeps a whole process rather
than a descriptor. That sets a feasibility floor:

```
budget > live working set + (39 MB x parked tabs)
```

Above it the design does what it claims. Below it, it degrades toward discard-LRU.
